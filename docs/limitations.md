# Known limitations

## The threshold detector fits once and never refits

`ml/tasks.py`'s `_check_resource` fits each resource's `ThresholdDetector`
exactly once, after `FIT_WINDOW_COUNT` (30) bootstrap windows of history,
and never refits it afterwards. This is deliberate -- a later fault can't
drag the baseline up to absorb itself -- but it means:

- A fault injected during the ~5-minute bootstrap window corrupts that
  resource's baseline permanently; the detector never gets a second chance
  to fit on clean data.
- Legitimate drift in normal behavior over time (e.g. a slow traffic
  increase) is never absorbed into the baseline -- it will eventually look
  like a permanent anomaly.
- A resource that starts being polled for the first time always has this
  same cold-start window, with no guard against a fault happening to land
  inside it.

See `ml/tasks.py`'s module docstring for the rationale.

## The live detection task bootstraps on far less history than the harness

`ml/tasks.py` fits after `FIT_WINDOW_COUNT` (30) windows — about 5 minutes at
the production 10-second collector interval. The Week 10 harness fits on the
70% train slice of a multi-day dataset, which is tens of thousands of windows
spanning several full daily cycles.

Those are not the same detector in any meaningful sense. The harness fit has
seen every phase of the seasonality curve; the live fit has seen five minutes
of one phase, so its per-signal spread is far too narrow and its first few
hours will over-trigger as load drifts away from whatever it bootstrapped on.
Any precision/recall number from the harness is therefore an upper bound on
live behaviour, not a prediction of it. Raising `FIT_WINDOW_COUNT` to cover a
day, or refitting on a rolling window, is the obvious fix and is in tension
with the fit-once rule above — it needs a decision, not a patch.

## `uptime_seconds` is collected but no detector uses it

It is one of the 20 canonical signals, and the informative part of it is the
*drop* when a resource restarts. Every detector here scores the latest value
of each signal, and the latest value of a monotonic counter only encodes "time
since the last restart" — fitted on it, a detector learns a ramp and flags the
passage of time. So `core/signals.py` keeps it out of `DETECTOR_SIGNALS`
entirely, which means restarts are currently invisible to detection even though
the data to see them is being recorded. A detector that differences the signal
would close this.

## Datasets v1–v3 use retired signal names

They were generated before `docs/metric-schema.md` became the single metric
list, so they carry the old names and units from `docs/notes/old-metrics.md`
(`cpu_pct`, `error_rate_pct` as a percentage rather than a fraction, and so
on). Their manifests are marked `deprecated`. They cannot be regenerated by the
current `make_episodes.py` and are not comparable with v4 and later; they are
kept only for provenance, and because v2 is the evidence behind the seasonality
finding in `docs/results/practice-run.md`.
